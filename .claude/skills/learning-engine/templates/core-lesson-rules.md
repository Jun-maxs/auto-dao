> [!WARNING]
> Reader-first 参考文档：当前项目默认采用 learn-first。本文不再作为旧 core 流程的直接生成入口，但其中“短、顺、像懂行朋友讲明白”的写作规则可作为 learn-card 的风格参考。

> 本文档是旧版 `lesson-template.md`（深入版/Deep）的配套档，曾用于指导 AI 生成**精华版/Core** 教程。

> **历史触发条件（仅供理解旧会话）**：用户在启动课程时说 "先给我精华版" / "核心版先来" / "先写 core"，或明确希望"用一份短文档把整块专题讲完"。

## 〇、这份文档是什么，不是什么

**是**：

- 一份**写作规则**——告诉 AI 精华版的风格、结构、取舍
- 配套一个**可复制骨架**（§九）——起手即用
- 一张**DROP/KEEP 对照表**（§五）——避免把 deep 版换皮当精华版

**不是**：

- 不是 `lesson-template.md` 的替代品——深入版仍由老模板承载
- 不是自动生成器——AI 仍需按用户资料内容做判断
- 不是 cheatsheet——精华版是**一篇连贯的文章**，不是要点堆砌

**参考样本**：`plan/教程优化.md`（用户手写的 I2C 精华版）——本文所有示例均引自该文或原 deep 版 `learning-history/003_stm32f103-hal_2026-04-13-09-45/lessons/02.0/02.1/02.2`。

## 一、核心哲学

### 1.1 一句话定位

> **精华版 = 一位懂行朋友花 20 分钟把整块专题给你讲明白，让你带走可用的心智模型。**

不是"把 2400 行压缩成 240 行的摘要"，而是**重新讲一遍**——以"为什么这样设计 → 怎么用"的因果链，把散落在多个文件里的知识点揉成一个**完整的故事**。

### 1.2 三条黄金准则

1. **深度 > 广度**：选 1 个关键机制讲透，不要并列罗列所有细节
2. **心智模型 > 知识点清单**：给 1 个能分类未见过场景的分类框架（如 I2C 的 A/B/C 类），而非背 10 个外设的 API
3. **因果 > 列举**：每讲一个结论，前面要有"为什么不得不这样"的推导——禁止"请记住 X"式命令

### 1.3 自检问题（写完后自问）

- [ ] 学员读完能回答"为什么发明这个"吗？（不是"这个是什么"）
- [ ] 学员能把这套知识**用一个比喻**讲给同事听吗？（有没有标志性类比）
- [ ] 给学员一个资料里没出现过的新外设/新场景，他能套用本文的分类框架吗？
- [ ] 学员读完后，能**独立跑起来**一段最小可运行代码吗？
- [ ] 删掉哪一段都会让故事断链？（如果某段删了毫无影响，那段就该删）

## 二、目录分层与命名

### 2.1 标准目录结构（2026-04-19 启用）

```text
learning-history/{topic}_{timestamp}/lessons/
├── core/                              ← 精华版（默认先出）
│   └── 02_I2C 精华版.md               ← 把 deep 的 02.0/02.1/02.2 精华合成一篇
└── deep/                              ← 深入版（Pro，按需触发）
    ├── 02.0_I2C 协议原理.md
    ├── 02.1_I2C 协议代码.md
    └── 02.2_I2C 外设实战速查.md
```

**规则**：

- **默认合并**：一个专题（如 I2C）的精华版**原则上只生成 1 个 md 文件**，把 deep 里的原理+代码+实战揉成一篇
- **允许拆 2 篇**：若专题真的太大（精华版超过 350 行），可拆为 `02A_原理.md` + `02B_代码与实战.md`，但**不得超过 2 篇**
- **禁止 3 篇以上**：如果精华版要拆 3 篇，说明没真正精简——应回去砍内容
- **deep/ 原结构不变**：继续用现有 `NN.X_描述.md`（`02.0/02.1/02.2`）的命名约定

### 2.2 精华版命名模板

```text
{NN}_{主题}精华版.md         # 单篇
{NN}A_{主题}·{侧重}.md        # 两篇时的 A 篇
{NN}B_{主题}·{侧重}.md        # 两篇时的 B 篇
```

**示例**：

- `02_I2C 精华版.md`
- `03A_SPI·协议与电气.md` + `03B_SPI·代码与实战.md`
- `04_CAN 精华版.md`

### 2.3 session_state.json 记录

```json
{
  "lesson_files_core": ["core/02_I2C 精华版.md"],
  "lesson_files_deep": ["deep/02.0_I2C 协议原理.md", "deep/02.1_I2C 协议代码.md", "deep/02.2_I2C 外设实战速查.md"]
}
```

兼容旧字段 `lesson_files`：若只有旧字段，默认指向 deep/。

## 三、结构骨架：六幕剧（不是六章节）

精华版**不用** `一、二、三、四` 形式的章节号，改用"**第 N 幕**：{问题或目标}"作为小节标题。幕名**必须是一个问题或目的**，不得是名词短语。

### 3.0 开篇 FAQ：先让读者把疑问冒出来（2026-04-19 新增）

**位置**：第一幕**之前**，放在开头引子 / "读前提醒"（如有）之后。作为全文的正式起点。

**为什么必要**：读者在读第一幕讲"发明动机"时还没见过具体术语（如 `CPOL/CPHA`、`仲裁`、`DE/RE`）——一到第二三幕被这些名词砸憵。FAQ 的作用是给即将出现的专有名词**预留一个"字面意义钩子"**，让读者后面读到时心里有预期"哦就是那个东西"。

**结构**：

```markdown
## 💡 开篇先问（FAQ）：带着这些问题往下读

{1-2 句引子，告诉读者这一节的用法。}

1. **Q：{读者视角的直白问题}**  
   → {1-2 行字面答案，带关键术语的字面含义}（第 N 幕讲透）

2. **Q：...**  
   → ...（第 N 幕讲透）

...（3-5 条）

---
```

**问题选材必须覆盖 3 类**（3-5 条总量里至少各占 1 条）：

| 类型 | 示例 | 作用 |
|-----|------|-----|
| **动机质疑类** | "I2C 不够用吗？为啥还要 SPI？" | 建立"学它的必要性"，避免"被迫学" |
| **术语字面类** | "CPOL/CPHA 这两个大写字母组合到底是啥？" | 给专有名词预埋字面含义 |
| **常见误解类** | "RS485 是新协议吗？跟 UART 什么关系？" | 排除先入为主的错误预期 |

**硬性约束**：

- **3-5 条**——少于 3 信息不够，多于 5 就成了摘要
- **每条答案 1-2 行**（单行最佳）——超过就成了知识点而非引子
- **每条答案必须指向后续章节**（用"（第 N 幕讲透）"或类似定位）
- **问题用"你 / 我 / 我们" 口吻**，绝对不用"本文将介绍..."这种元语言
- **术语在 FAQ 里只给字面含义**，**不展开推导**（推导留给对应章节）

**反模式（生成时必避）**：

- ❌ FAQ 写成 3 行以上的长答题（那是 lesson 本体，不是引子）
- ❌ FAQ 问"这节讲什么"（过于元层，读者真正的疑问是名词/场景层面）
- ❌ 所有 Q 都问"为什么"（缺术语字面类，无法预埋钩子）
- ❌ 答案详细到不用读后续（失去"引子"作用，变成"剧透"）

### 3.1 标准幕结构

| 幕 | 职责 | 长度占比 | 示例标题（引自 教程优化.md） |
|---|------|--------|---------------------------|
| **开篇 FAQ** | 3-5 条读者视角问答，给术语预埋钩子 | ~5% | `💡 开篇先问（FAQ）：带着这些问题往下读` |
| **第一幕** | 动机：为什么发明/需要这个 | ~10% | `第一幕：为什么要发明 I2C？` |
| **第二幕** | 最底层核心机制（物理/电气/数据） | ~15% | `第二幕：物理层——2 根线怎么让多个设备不打架？` |
| **第三幕** | 逻辑/协议层 | ~25% | `第三幕：协议层——两根线如何传递有意义的信息？` |
| **🧠 Mid-check** | 3 题默答自检（不收卷） | ~3% | `先停一下——自检` |
| **第四幕** | 从理论到 API/代码的抽象层 | ~15% | `第四幕：从协议到代码——HAL 帮你做了什么` |
| **第五幕** | 2-3 个实战外设/案例，凝结成心智模型 | ~20% | `第五幕：三个外设——把三种模式装进大脑` |
| **第六幕** | 关键要点提炼（希望学员背下来） | ~7% | `第六幕：关键要点提炼（我希望你把这些背下来）` |
| **结尾 · 出口** | 出口检查题 / Next-step menu（二选一或并存，详见 §3.4） | ~5-8% | `你现在先完成 5 个检查题` / `我建议你接下来：...` |

### 3.2 幕数可伸缩（4~7 幕）

- **概念性专题**（偏原理，如"什么是卷积"）：可压缩到 4 幕（动机 + 直觉 + 机制 + 要点）
- **操作性专题**（偏代码，如"HAL GPIO"）：可压到 5 幕（动机 + 硬件 + API + 实战 + 要点）
- **大型综合专题**（如 I2C 这种横跨协议+代码+多外设）：6-7 幕
- **绝不 8 幕以上**：八幕就是 deep 版，请回去生成 `lesson-template.md` 的版本

### 3.3 Mid-check 的硬要求

**位置**：在"抽象概念高峰"之后、"代码实战"之前（通常第三/四幕之间）。

**格式**：

```markdown
---

## 🧠 先停一下——自检

请你默答三个问题（对应资料里的核心问题）：

1. **{问题 1}**？（提示：{关键词}）
2. **{问题 2}**？
3. **{问题 3}**？

如果答得上来，{前面几幕}就过关了。答不上来也没关系，翻回去看对应段落。

---
```

**关键约束**：

- **3 题**（不是 2 不是 5）
- **不留空槽**（不是填空题，学员心里默答）
- **不给标答**（硬约束：引导回去重读对应段，不抄答案）
- **题目来自本课已讲过的核心推导**（不得超纲）

### 3.4 结尾形态：Exit-check / Next-step menu / 并存

精华版**不能断头**——第六幕讲完要点之后，必须要么让学员"带问题去验证"，要么让学员"带行动去下一步"。两种模式对应**两种不同的学员画像**，也对应 core/deep 分层的**两种不同桥接**。

#### 3.4.1 两种结尾的选用决策

| 特征 | 选 **出口检查题**（Exit-check） | 选 **Next-step menu** | 选 **并存**（推荐） |
|------|----------------------------|----------------------|-------------------|
| 适用学员 | 自主阅读型：想先自测、再带着问题去 deep 求证 | 交互引导型：希望 AI 下一步继续带路 | 两者皆可；给学员留选择 |
| deep 版状态 | **已存在**（能真正去查） | 尚未生成 / 本课不涉 deep | deep 已存在且 Next-step 有价值 |
| 与 Mid-check 关系 | 呼应且升级——Mid-check 默答，Exit-check 收笔 | 不呼应——菜单不是测试 | Exit-check 在前，Next-step 在后 |
| 认知张力 | **高**——未解答的问题驱使去 deep | 中——给选项是"邀请"而非"悬念" | 最高——先悬念后邀请 |
| 风险 | 题出不好会挫败学员 | 选项空泛会失去菜单意义 | 篇幅偏长（控制在 8% 内） |

**默认策略**：若 deep 版已存在 → **并存**；若 deep 未生成 → 只用 Next-step menu。

#### 3.4.2 出口检查题（Exit-check）的硬要求

**位置**：第六幕"关键要点"之后，Next-step menu 之前（若并存）或文末（若单用）。

**格式**：

```markdown
---

## 你现在先完成 {N} 个检查题

请把答案写到本会话的 `answers/{lesson_stem}.md` 文件里；我会读取这个文件批改，并根据结果{继续带你往下学 / 带你去 deep 版对照答案}。

### 题 1

{问题}

{可选：提示或约束}

---

### 题 2

{问题}

...
```

**关键约束**：

- **3-5 题**（少于 3 分量不够，多于 5 变成小测打断节奏）
- **至少 1 题的答案必须在 deep 版中能查到**——这是"带去 deep 求证"张力的核心。若本课无对应 deep 版，应降级为 Next-step menu
- **至少 1 题考察跨节整合**（不是第 N 幕原文复述；例如 I2C 的"第 4 题：这个时序在做什么？"整合了 §3+§5 的复合读写 + 内部地址）
- **可以包含"改错题"**（给出一句错误说法，让学员指出错在哪）——这是呼应 §4.3 工具 5 "就地纠错"的最佳载体
- **不在同一文件里披露答案**——答案留在 deep 版，或等学员给答复后 AI 再批改
- **答案必须文件驱动**——引导学员写入 `answers/{lesson_stem}.md` 或对应 notes 文件，禁止要求"直接发给我"、"在聊天里回答"、"按编号直接回复"
- **引导语必须出现**"带你" 字样（`继续带你往下学` 或 `带你去 deep 版对照答案`），保持带路朋友的口吻连续
- **标题用"题 N"而非"问题 N"/"Q N"**——与"检查题"的定位一致

**反模式**：

- ❌ 题目是第 N 幕的原文复述（学员翻回去就能抄）
- ❌ 给标答或"点击展开"折叠答案（精华版里披露答案会瓦解"去 deep 求证"的张力）
- ❌ 超过 5 题（变成小测，精华版不是测试卷）
- ❌ 只有概念回忆题，没有任何一题需要综合推导

#### 3.4.3 Next-step menu 的硬要求

**位置**：文末（若与 Exit-check 并存，位于 Exit-check 之后）。

**格式**：

```markdown
---

## 我建议你接下来：

这个知识体系有点深，一次性全部吸收不太现实。你可以告诉我**你想深入哪一块**，我给你展开：

1. 想做练习题（资料里 {章节} 有 {题数} 道新情境测试题）——我可以当你的批改教练
2. 想更深理解某一个机制——比如 "{具体机制问题}"、"{另一个机制问题}"
3. 想直接动手写代码——我可以帮你把 {外设 1} / {外设 2} 驱动拼起来、分析每一行
4. 想做一个"陌生外设迁移"练习——比如给你一段 {外设} 的数据手册描述，你判断 API 选型

你想从哪儿开始？
```

**硬约束**：

- **必须 3-4 个选项**（给 ≥ 5 个会让人选择瘫痪，≤ 2 个失去菜单的意义）
- **每个选项必须指向具体动作**，不能是"继续学下一课"这种空话
- **第 4 个选项通常是"迁移/应用"**（考察泛化，是精华版→deep 版的天然桥梁）
- **结尾问句**："你想从哪儿开始？"（把主动权交还给学员）
- **与 Exit-check 并存时**：两者之间用 `---` 分隔；Next-step menu 的选项 1 可以写作 "想让我批改你刚才的 {N} 道检查题"，自然衔接

## 四、语气与叙事手法

### 4.1 开场套路（必用其一）

**A 式·带路式**：

> 好，咱们一起把这三份资料系统性地过一遍。我不会复述原文，而是带你按**"为什么这样设计 → 怎么用"** 的因果链走一遍……

**B 式·场景式**：

> 想象你手头有一块 STM32，要同时挂一个 EEPROM、一个温湿度传感器、一个 OLED 屏……

**C 式·反直觉式**：

> 你大概听说过 I2C 只要两根线。但两根线怎么挂多个设备不打架？这才是这协议最精妙的地方。

**禁止**：

- ❌ `# Lesson 02: I2C 协议原理`（官方教材口吻）
- ❌ `**时间**：xxx **目标认知层级**：xxx`（元信息表头）
- ❌ `本节课结束后，你应该能够：...`（空洞学习目标）

### 4.2 第二人称贯穿全文

- ✅ "**你**要读某个抽屉的内容，需要两步"
- ✅ "新手 90% 的 HAL_ERROR 都是**你**这里传错了"
- ❌ "学习者需要理解……"
- ❌ "本节引导用户掌握……"

### 4.3 五种高密度叙事工具

#### 工具 1：标志性类比（每个核心概念 ≤ 1 个）

好类比的标准：**熟悉领域 + 映射精确 + 一记就牢**。

| 概念 | 类比（来自 教程优化.md） |
|------|---------------------|
| 开漏+上拉+线与 | "会议室的灯，只有下拉开关，谁按谁关灯；没人按时，弹簧把开关拨回'开'。两个人同时按？灯还是关着——不打架。" |
| 7 位地址 | "每个 I2C 设备有自己的 7 位地址（像手机号）" |
| 设备地址 vs 内部寄存器地址 | "设备地址像'门牌号'，内部地址像'门后的第几个抽屉'" |

**禁止**：一个概念连用 2 个类比（会稀释印象）、类比对象超纲（如用量子力学解释上拉电阻）、中途换类比（同一概念全文用同一个类比）。

#### 工具 2：反事实论证（揭示"为什么不得不这样"）

**骨架**：`如果不这样 → 会发生 {具体后果} → 所以必须这样`

示例（来自 教程优化.md §二）：

> 如果多个设备都挂在同一根 SDA 上，A 想输出高，B 想输出低，电源经 A 直接短路到地经 B，**瞬间烧片**。

禁止模糊化："如果不用开漏，会有很多问题"——**必须具体**到"烧片"、"数据错乱"、"HAL_ERROR"这类可观测后果。

#### 工具 3："一句话记住" + "血的教训"

**一句话记住**：每一幕末尾给一个可背的金句。

> **一句话记住**：I2C = 少引脚换速率的总线方案。
>
> **这是 I2C 能"多设备共享两根线"的根本原因。**

**血的教训**：在最容易踩坑的地方用对话语气警告。

> 血的教训：新手 90% 的 "HAL_ERROR" 都是这里传错了。**一定定义宏**：……

#### 工具 4：回扣指路（前后文桥梁）

每讲一个新概念，**必须**回指前面哪里埋了伏笔、下面哪里会用到。

示例：

> 记住这个"**两次起始**"的形状，它就是后面 `HAL_I2C_Mem_Read` 的物理实现。

```markdown
看最后一行——`HAL_I2C_Mem_Read` 的波形**一比一对应** 3.5 节讲的复合读写。**API 不是语法糖，它就是协议的代码化**。
```

这是精华版**最关键**的手法：不断把新知识点焊回前面的推导，让整篇文章是一个单连通图而不是知识点列表。

#### 工具 5：就地纠错（当源资料有可验证错误时）

精华版的"懂行朋友"有**判断力**。源资料（用户给的 PDF、用户的答题记录、原 deep lesson）里如果有技术错误，**视而不见反而会毁掉可信度**——读者迟早会独立发现错误，一旦发现你没指出来，他会开始怀疑"你是不是也没看懂"。就地温和纠正，才让读者放心"你真的懂"。

**适用条件**（三者必须同时满足）：

1. 错误是**可验证的**技术错误或术语误用（不是风格/口味之争）
2. 错误落在**本课核心推导路径**上（与主线无关的细节可以放过）
3. 你能给出**正确说法的依据**（数据手册、协议规范、物理定律、计算过程）——不能是"我觉得应该"

**标准格式骨架**：

```markdown
这里顺便纠正你材料里一个答案：

> {错误原文或错误结论}

{1 句说明为什么错}

**正确应当是**：

{正确说法 + 1 句依据}
```

**示例**（引自 `learning-history/003_stm32f103-hal_2026-04-13-09-45/lessons/sugeladi/i2c精华.md`）：

> 这里顺便纠正你材料里一个答案：
>
> ```text
> 0b0111000 = 0x38
> 写地址 = 0b70
> ```
>
> 不是 `0b70`。二进制里只能有 `0` 和 `1`，`0b70` 这种写法不合法。
> 正确的是：`写地址 = 0x70`（即 `0x38 << 1`）。

**硬约束**：

- **必须可验证**：纠错必须附上依据（规范引用 / 物理推导 / 计算过程），不得凭感觉
- **态度克制**：用 `"这里顺便纠正..."` / `"更准确地说是..."` ——不说 `"材料是错的"` 这种绝对化表达
- **上限 3 处**：同一篇精华版**最多 3 处纠错**。超过说明资料质量太差，应在文末 Next-step menu 里建议用户换资料或标注资料局限
- **禁止编造**：不确定时宁可不纠错——编造纠错会**彻底毁掉**带路朋友的可信度（比不纠错的伤害大 10 倍）
- **与 Exit-check 联动**：纠错的点可以作为 Exit-check 的"改错题"素材（§3.4.2），让学员自己辨识同类错误

**反模式**：

- ❌ 纠正拼写/标点等无关细节（转移读者注意力，挑不到点上）
- ❌ 一次纠 5 处以上（变成找茬而非带路）
- ❌ 用 "众所周知" / "显然" 作为纠错理由，不给具体依据
- ❌ 在非核心推导路径的段落纠错（读者会迷惑"这纠错跟主线什么关系"）
- ❌ 纠错后不给正确说法（只骂不给药）

## 六、代码与视觉资产纪律

### 6.1 代码段：只给"协议代码化"那一行

精华版**不**展示完整函数，只展示**让学员看完协议后"啊原来这就是代码"** 那一行。

**好示例**（来自 教程优化.md §5.3）：

```c
uint8_t cmd[3] = {0xAC, 0x33, 0x00};
HAL_I2C_Master_Transmit(&hi2c1, AHT20_ADDR_W, cmd, 3, 1000);
HAL_Delay(80);
uint8_t raw[7];
HAL_I2C_Master_Receive(&hi2c1, AHT20_ADDR_R, raw, 7, 1000);
```

5 行代码对应"发命令→等采样→读结果"三段式——**再 1 行废话都不加**。

### 6.2 血的教训式宏定义

所有"新手最容易踩"的魔数，用 `#define` 配合反事实注释展示：

```c
// 数据手册说 7 位地址是 0x50？
// ❌ HAL_I2C_Mem_Write(&hi2c1, 0x50, ...)      // 错！会被当成地址 0x28
// ✅ HAL_I2C_Mem_Write(&hi2c1, 0x50 << 1, ...) // 对，传 0xA0
```

### 6.3 协议时序：ASCII 优先

**协议时序**默认用 ASCII 文字图（可复制、可编辑、可 diff）：

```text
S → ADDR(N,W) → A → 内部地址 → A → Sr → ADDR(N,R) → A → 数据 → N/A → P
└──── 第一次（设指针）────┘    └──────── 第二次（读数据，不释放总线）───────┘
```

**规则**：

- 技术符号（`S`、`ADDR`、`ACK`、`HAL_I2C_Mem_Write`）**必须英文**保持对齐
- 中文注解只出现在：图**正下方**的阶段说明 或 **括号内**的语义标签
- （与 `SKILL.md §4.2 排版可读性规则 #8` 一致）
- **何时放弃 ASCII → 用真实图片**：见 §6.4 决策表（如 SPI CPOL/CPHA 四模式波形、CAN 位时序、MOSFET 电平转换电路等——这些用 ASCII 画出来会扭曲）

### 6.4 图片/图表：关键节点的可视化补强（2026-04-19 新增）

精华版**不是纯文字文档**。在少数关键节点，一张图胜过 200 字文字。但**滥用图片会让精华版蜕化成幻灯片**——必须按本节决策表筛选。

#### 6.4.1 图片使用优先级

按优先级从高到低评估，**命中即停**，不向下走：

| 优先级 | 条件 | 动作 |
|-------|------|------|
| **P1** | `{session_dir}/image_index.json` 中有资料原图直接对应本幕核心概念（匹配度：章节标题相似度 ≥ 0.6 或关键词重合 ≥ 2 个） | **直接引用 PDF 原图**：`![{caption}](../images/{hash}.jpg)` |
| **P2** | 资料无直接原图，但概念属于 §6.4.2 列出的"**强制图示白名单**"（如 CPOL/CPHA 四象限、CAN 帧结构） | 生成 **1 张 DrawIO**：`![{caption}](../diagrams/{slug}.png)` |
| **P3** | ASCII 文字图足以精确表达（如 I2C 起始/停止、UART 起止位） | **不画图**——ASCII 优于图片（可复制） |
| **P4** | 表格足以清晰对比（如四大总线物理层对比） | **用表格**——不画流程图 |

#### 6.4.2 强制图示白名单（出现这些概念时必须配图）

精华版里**只有下列概念**强制配图，其他概念原则上**不配图**（文字/ASCII/表格足够）：

| # | 概念类型 | 示例 | 为什么必须配图 |
|---|---------|------|-------------|
| 1 | 带 2 个正交维度的枚举（如时钟极性×相位） | SPI CPOL/CPHA 4 象限 | 文字描述会把学员绕晕；一张 2×2 象限图 10 秒看懂 |
| 2 | 多字段二进制帧 | CAN 数据帧（SOF+ID+RTR+DLC+Data+CRC+ACK+EOF）、Modbus RTU 帧 | 字段位宽的比例关系文字写不清 |
| 3 | 电气/硬件拓扑（≥ 3 节点） | RS485 多从机总线、CAN H/L 差分线 | 空间关系用文字描述低效 |
| 4 | 2D/3D 波形（横时间纵电压+相位） | CAN 位定时（SS+PropSeg+PS1+SamplePoint+PS2）、差分信号波形 | 时序 + 电平 + 位置三维信息 |
| 5 | CubeMX 关键一屏配置（**最多 1 张**） | SPI 时钟分频+CPOL/CPHA+数据大小的合成界面 | 参数间的联动关系一张图清晰 |

#### 6.4.3 图片引用与存放（与 deep/ 一致）

**路径规则**（与 `SKILL.md §4.2.1` 完全一致，避免两套标准）：

| 图类型 | 引用语法 | 物理解析结果 |
|--------|---------|-------------|
| PDF 原图 | `![{caption}](../images/{hash}.jpg)` | `{session_dir}/images/{hash}.jpg` |
| AI 生成 DrawIO | `![{caption}](../diagrams/{slug}.png)` | `{session_dir}/diagrams/{slug}.png` |

注意 core lesson 位于 `{session_dir}/lessons/core/NN_xxx.md`，**相对路径是 `../../images/`？**

- ❌ **错**：core 文件在 `lessons/core/` 下，`../images/` 会解析到 `{session_dir}/lessons/images/`（不存在）
- ✅ **对**：正确写法是 `../../images/{hash}.jpg` 和 `../../diagrams/{slug}.png`

**核心约束**：

- 图片 caption 必须描述"图在教什么"，不是"图是什么"——如 ✅ `SPI 四模式时钟极性与相位示意` vs ❌ `SPI 时序图`
- DrawIO 文件命名小写 snake_case 英文 slug（如 `spi_cpol_cpha_matrix.drawio`），禁止中文/空格
- 生成 DrawIO 前必须先读 `image_index.json`（违反则触及 §6.6 禁止项第 4 条）

#### 6.4.4 每篇精华版的图片数量上限

| 专题规模 | 图片数量上限 | 备注 |
|---------|-------------|------|
| 单 lesson 级（150 行以下） | 0-1 张 | 优先零图，只在 P2 白名单命中时才放 |
| 多 lesson 综合（150-250 行） | 1-3 张 | 核心幕各 1 张，非核心幕不配图 |
| 超大专题（250-350 行） | 2-4 张 | 不得超过 4 张 |

**超过上限 = 蜕化成幻灯片**。精华版的信息密度核心是文字 + ASCII + 表格的组合，图片是"压不下来才出场"的补强。

### 6.5 禁止项

- ❌ 不放超过 15 行的单段代码块
- ❌ 不重复展示"同一骨架的变体"（deep 版才做 3 个外设各来一遍）——精华版**用一个骨架+分类**统一
- ❌ 不跳过 `image_index.json` 资料原图检索就自己生成 DrawIO（同 `SKILL.md §4.2.2` 禁区 #11）
- ❌ 不在**非白名单**概念（§6.4.2）上塞图——如 I2C 起始/停止信号、UART 起止位这种 ASCII 能表达清楚的，不许配图
- ❌ 不把 PDF 原图当"装饰"随意插入——每张图必须能独立回答一个具体问题（如"CPOL=0 时 SCK 空闲电平是？"）
- ❌ 不把 CubeMX 3 屏幕截图全放（最多 1 张合成关键一屏）

## 七、长度与节奏

### 7.1 硬性长度约束

| 专题规模 | 精华版目标长度 | 对应 deep 长度 | 压缩比 |
|---------|-------------|--------------|-------|
| 单 lesson 级（如 "GPIO 基础"） | 100-150 行 | 400-600 行 | ~1:4 |
| 多 lesson 综合（如 "I2C 全套"） | 150-250 行 | 1500-2500 行 | ~1:10 |
| 超大专题（如 "整个通信总线对比"） | 250-350 行 | 3000+ 行 | ~1:10 |

**超过 350 行 = 写砸了**，回去砍内容，不要硬加。

### 7.2 节奏检查

每写完一段，问自己：

- 这段**讲了什么新东西**？（讲不出就删）
- 这段**和前面哪段呼应**？（孤立段落打断节奏）
- 读者看到这段会**点头还是皱眉**？（要的是"哦原来如此"不是"嗯……继续看吧"）

## 八、反模式（写到这样要回炉）

### 反模式 1：deep 版换皮

**症状**：把 deep 版的每节抽 1-2 段，拼成"压缩版"。保留了大节标题 `一、二、三`，也保留了`**学习目标**:`、`**前置依赖**:`之类的头部。

**判定**：如果精华版保留了 ≥ 3 条 `lesson-template.md §〇-§二` 的结构元素，就是这个病。

**治疗**：推倒重写，按第三幕（§三）的"六幕剧"骨架重组。

### 反模式 2：要点 bullet 化

**症状**：全文变成 "- XXX\n- YYY\n- ZZZ" 的要点列表，没有叙事。

**判定**：连续出现 3 个以上 `- ` 开头的 bullet（不带上下文段落）就是这个病。

**治疗**：把 bullet 展开成段落或改成表格；bullet 只在**第六幕的 key takeaways** 和实战外设的**硬约束清单**里允许用。

### 反模式 3：类比贪多

**症状**：一个概念接连用 2-3 个类比。"它像工厂的流水线，也像邮局的分拣，又像…"

**判定**：同一概念出现 ≥ 2 个类比。

**治疗**：**选最好的那个，删其他**。类比的力量来自唯一性。

### 反模式 4：禁区教学（套用自 `SKILL.md §4.2.2`）

- ❌ 用术语解释术语
- ❌ 跳过推理中间步骤（"显然"/"不难看出"/"容易证明"）
- ❌ 编造函数名/API 参数
- ❌ 引入未铺垫的前置概念

**注**：精华版对"禁区教学"的容忍度**更低**——因为精华版没有 `二、知识回引` 来补漏，凡是读者看不懂的地方全都暴露。

### 反模式 5：Mid-check 形式化

**症状**：Mid-check 的 3 题是"复习题"，答案就在前 2 段。

**治疗**：Mid-check 应考察**跨节整合**——如 I2C 的 mid-check 第 3 题是"复合读写的两次起始，第一次传什么第二次传什么"，需要把 §3.3 + §3.5 的知识组合起来。

### 反模式 6：Next-step menu 含糊

**症状**："1. 继续学习；2. 复习本课；3. 其他问题"。

**治疗**：每个选项**指向具体内容**。参考 教程优化.md 文末的 4 个选项，每个都有可执行的具体动作（做题/展开某机制/写代码/迁移练习）。

### 反模式 8：术语凭空出现（2026-04-19 新增）

**症状**：

- 第一幕讲完动机，第二幕直接蹦出 `CPOL/CPHA`、`仲裁`、`DE/RE`、`显性/隐性` 这种专有术语
- 读者第一次见到名词时心里没有任何预期，必须停下来猜"这是啥"
- 整篇文档**不含开篇 FAQ 部分**（第一幕之前直接是正文）

**判定**：

- 整篇没有 §3.0 规定的 `## 💡 开篇先问（FAQ）` 节
- 或 FAQ 节不到 3 条，或某条答案超过 3 行
- 或 FAQ 三类问题（动机质疑/术语字面/常见误解）有类未覆盖

**治疗**：按 §3.0 格式补 FAQ。通用公式是：

1. 列出第二/三幕最早出现的 3-5 个专有名词
2. 为每个名词写一个读者会问的问题（模拟一个从未学过的学员的语气）
3. 至少再加 1 条"为什么要学" 的动机质疑问题
4. 再加 1 条"常见误解" 问题（如"X 和 Y 是一回事吗？"）
5. 每条答案 1-2 行，并指向后续章节

---

### 反模式 7：图片喧宾夺主（2026-04-19 新增）

**症状**：

- 精华版里出现 ≥ 5 张图
- 每幕都配图
- 在 §6.4.2 白名单**之外**的概念上配图（如给 I2C 起始信号配图）
- 图 caption 是"时序图"/"结构图"这种描述性而非教学性文字
- 图片直接复用 deep/ 的全部资产，没有筛选

**判定**：图片数量 > §6.4.4 上限，或有图不在 §6.4.2 白名单。

**治疗**：按 §6.4.1 优先级重新筛选：

1. 每张图单独问："删掉这张图，读者能不能通过文字或 ASCII 理解这段？" 能理解就删
2. 保留的图按"强制图示白名单 §6.4.2"逐条对应——对应不上就删
3. 最终总数不能超过 §6.4.4 上限

## 附录 A：从 deep/ 蒸馏到 core/ 的实操流程

当 deep 版已存在、需要补写精华版时：

### 步骤 1：读完所有 deep/ 文件，在纸上画一张**因果图**

节点是核心概念，箭头是"为什么导致"。例如 I2C：

```text
多设备共享 → 需要仲裁 → 开漏+上拉 → 线与 → 不会短路
                              ↓
                          软限高电平 → 必须用边沿而非电平做边界 → 起始/停止信号
                              ↓
                          SCL 高稳定规则 → 跳变 = 边界
```

这张因果图**就是精华版的骨架**——每个箭头都是一幕的"推导链"。

### 步骤 2：每个 deep 章节只保留 1 句话进精华版

- deep `§3.2 物理层` 7 条规则 → 精华版保留"开漏+上拉+线与"一条
